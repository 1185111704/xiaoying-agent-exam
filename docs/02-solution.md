# 02 方案设计

## 1. 设计原则：程序只否决，不替模型选路线

这道题有两条要求互相牵制：

- **ReAct 决策要求**：题目规定"仅有固定条件分支不算完成"，所以下一步做什么必须由模型决定。
- **关键缺陷不能出现**：越权发布、虚报保存成功都是硬伤，所以不能把底线押在模型自觉上。

解决办法是按两个层次分工：

| 层 | 负责什么 | 判定依据 |
|---|---|---|
| 程序（工具与守卫） | 给出事实：字段缺不缺、规则有没有命中、时段有没有被占、保存成功没有。拒绝非法动作 | 客观、结果唯一 |
| 模型 | 选择下一步：补查还是打回，换哪个时段，请求确认还是阻断，失败后重试还是如实上报，什么时候结束 | 需要权衡 |

守卫拒绝一个动作时，**会把拒绝原因作为观察结果还给模型**，而不是由程序自己改走另一条分支。这样一来，"被拒绝之后怎么调整"本身就成了 trace 里可以看到的决策。

## 2. 调用流程

```
请求 ──▶ ReAct 循环（步数上限 N）
          │
          ├─ 模型选择工具 + reason
          ├─ 执行工具（守卫在这里拒绝非法动作）
          ├─ 观察结果追加进上下文
          └─ 模型决定下一步，或调用 finish
                 │
                 ▼
         报告汇总（程序从工具调用记录 + 数据库最终状态生成）
                 │
                 ▼
         输出 JSON + trace；存在待确认项时退出码为 2
```

工具返回错误时，**不自动重试**，也不由程序改走别的分支：错误码与原因作为观察交还模型，模型读懂后决定下一步（修参数、换时段、补查、请求确认、阻断，或如实上报失败）。真实运行中的例子见 [03-evaluation §3](03-evaluation.md#3-真实模型的动态决策)。

## 3. 工具集

每个工具都必须带 `reason` 参数，写明本步的决策依据，原样记入 trace。

| 工具 | 作用 | 返回要点 |
|---|---|---|
| `read_material` | 读取素材元数据 | 元数据、按档位标注的缺失字段、是否已在正式排期中 |
| `lookup_license` | 到版权库补查音乐或肖像授权 | found / not_found / expired（有效期不覆盖发布日期） |
| `check_rules` | 词表审核 | 命中列表：规则、严重度、原文证据 |
| `query_slots` | 查询账号在窗口内的时段 | 每个时段的状态：free / scheduled / held，以及占用者（排除本素材自己的占位） |
| `save_draft` | 保存排期草稿 | saved / unchanged / updated / conflict / rejected / failed，以及 draft_id 和版本号 |
| `request_confirmation` | 登记一个待确认项 | confirmation_id，以及**程序附加**的占用清单与可用的最近空位 |
| `block` | 阻断素材 | 记录阻断原因和证据 |
| `finish` | 结束本次运行 | 仍有素材没有结论时拒绝（`UNRESOLVED_ITEMS`）并列出素材；同一轮里 finish 后还有调用时也拒绝 |

"请求确认"、"阻断"、"结束"也都做成工具。这样它们会以结构化调用的形式出现在 trace 里，而不是夹在模型的自由文本中。

## 4. 保存层（本项目做深的部分）

### 4.1 save_draft 的守卫

下列情况一律拒绝（`status=rejected`），错误码和原因返回给模型。判定全部基于客观事实：素材数据、规则、请求、本次运行中**执行成功**的工具调用。

| 类别 | 错误码 | 条件 |
|---|---|---|
| 输入 | `INVALID_SLOT` | 时段不是补零的标准写法 `YYYY-MM-DD HH:00`，或不在 09:00–22:00 |
| 审核前置 | `ALREADY_SCHEDULED` | 素材已在正式排期中（重复提交） |
| | `BLOCKED` | 本次运行已阻断该素材 |
| | `FIELD_MISSING` | 缺少必需字段（账号、文案） |
| | `LICENSE_UNVERIFIED` | 需要的音乐/肖像授权未经 `lookup_license` 核实 |
| | `NOT_CHECKED` | 未做规则检查 |
| | `RULE_BLOCKED` | 命中阻断级规则 |
| 确认边界 | `FIXED_REQUIREMENT` | 改动了硬性要求（`fixed=true`） |
| | `EARLIER_THAN_REQUESTED` | 未给窗口时，替代时段早于要求时间（提前发布可能违反活动或保密时间） |
| | `OUTSIDE_WINDOW` | 超出用户给定的窗口 |
| | `CONFIRMATION_REQUIRED` | 时段与要求不同，却未标记 `needs_confirmation` |
| | `CONFIRMATION_MISMATCH` | 时段与要求一致，却标记了需要确认 |

通过守卫后进入存储事务；被占用则返回 `conflict` 并附占用者。

### 4.2 幂等

- 幂等键采用**业务键（素材, 账号）**：一个素材只保留一份活动草稿。
- 时段相同时再次保存，返回 `unchanged` 和原 draft_id，不写入任何数据。
- 时段不同时再次保存，在同一份草稿上把版本号加 1，并在同一事务里释放旧占位、占用新时段。
- **幂等键里不包含模型选出的时段。** 原因见 §6 的对比。

### 4.3 并发

查询结果只能作参考，以保存时的结果为准：模型查到某个时段空闲，等到真正保存时它可能已经被别人占了。

- 占位表以 `(账号, 小时)` 为唯一约束。不论有多少个进程，数据库层面都写不进第二条。
- 每次保存是一个事务：`BEGIN IMMEDIATE`（先拿写锁）→ 释放本素材的旧占位 → 插入新占位 → 写入或更新草稿 → 提交。
  - 违反唯一约束时整体回滚，返回 `conflict`，旧占位保持不变。
  - 写入出现异常时整体回滚，返回 `failed`，不会出现只占了时段、草稿却没存上的半成品。
- 锁等待上限 5 秒。超时返回 `failed`（存储繁忙），绝不报告成功。
- 保存失败后是否重试由模型决定，程序不自动重试。

## 5. 确认边界

**已实现：**

- "是否需要确认"由程序比较**库中草稿的时段**与**要求时段**得出，不采信模型自报的 `needs_confirmation`；该参数只用于保存时核对模型是否意识到自己改了时间（不一致即拒绝）。
- 指定时间被占：模型可以提出替代时段，但只能顺延（或在用户给定窗口内），草稿以 `pending_confirmation` 保存并占位。
- 硬性要求被占：不保存替代草稿，只能请求确认。
- 待确认项由程序附上占用清单（谁占了哪个时段、正式排期还是其他草稿）与可用的最近空位；退出码为 2。

**设计了但未实现（时间取舍）：** 第二轮 `--confirm C1=accept` / `--confirm C1=2026-11-03 21:00`，把同一份草稿推进为 `confirmed`（版本 +1），硬性要求只有拿到确认凭证才可改。见 [05-retrospective](05-retrospective.md)。

## 6. 方案对比与取舍

| 决策点 | 候选方案 | 选择 | 理由 |
|---|---|---|---|
| 幂等键 | 草稿内容哈希 / 请求哈希 / 业务键（素材, 账号） | **业务键** | 如果键里含模型选出的时段，重复提交时，自己的旧草稿会占住 19:00，模型于是改选 20:00，生成第二份草稿，正好与"只产生一份草稿"相反。用业务键的话，内容变化体现为升版本，不会新建草稿 |
| 存储与并发 | JSON 文件加文件锁 / SQLite / Redis 或 PostgreSQL | **SQLite** | Python 标准库自带，评审拿到可以直接运行；唯一约束加事务就能做到"检查+占位"的原子性，不用自己写锁。按需求量小的假设（A4），外部服务属于过度设计；以后切换到 PostgreSQL 时，表结构和约束可以直接沿用 |
| 时段与用户要求不一致 | 程序自动补上待确认标记 / 拒绝保存，交还模型 | **拒绝并交还模型** | 符合"只否决、不代选"的原则，模型的修正过程也会进入 trace |
| 确认方式 | 单轮，止步于待确认 / 两轮，用 `--confirm` 推进 | **设计为两轮，交付第一轮** | 第二轮能演示确认后同一草稿升版本；但在 3 小时内优先保证必须验收点与真实模型运行记录，第二轮列为未完成 |
| 替代时段往前还是往后 | 提示词里写偏好、由模型决定 / 程序守卫 | **程序守卫：未给窗口时只能顺延** | 真实运行中模型曾把 M01 从 18:00 改到 17:00。提前发布可能违反活动或保密时间，这是可客观判定的约束，应由程序把关；模型仍在可用时段中做选择。加守卫后的真实运行里，模型被拒一次后自行顺延到 19:00 |
| 报告中草稿信息的来源 | 本次运行的工具记录 / 数据库最终状态 | **数据库最终状态** | 草稿跨运行保留；只看本次记录时，上一轮存下且仍占位的草稿会被报成"未保存"。本次运行做了什么单列为 `draft.this_run` |
| 工具出错 / 业务不合法 | 程序自动重试 / 错误交还模型 | **交还模型** | 自动重试不属于 ReAct 决策；把错误码与原因作为观察返回，由模型决定修正、换方案或如实上报。由步数与调用次数上限兜底 |
| 运行中途等待用户输入 | 循环里读 stdin / 不读 | **不读** | 读 stdin 的话，测试和 trace 都无法复现 |
| LLM 语义审核 | 保留在规则检查里 / 砍掉 | **砍掉** | 所有验收点用词表都能覆盖；业务信息不足，语义规则只能靠编；把时间留给保存层 |
| 打回时附带什么 | 只给空闲时段 / 附上占用清单 | **附上占用清单，由程序自动附加** | 用户能看出时段是被正式排期还是被进行中的草稿占用，从而判断该换时间还是去协调。占用情况是客观事实，由程序在登记待确认项（以及改时段的草稿）时附上：占用清单 + 离要求时间最近的 3 个空位；不依赖模型在问题描述里转述 |
| "硬性发布要求"的含义 | 甲：用户的所有发布要求都是硬性的，"待确认"即满足"不擅自改变" / 乙：区分"指定时间"与"硬性要求"两级 | **乙** | 题干只有"未经用户同意不得擅自改变硬性发布要求"一句，未定义。参考实例中"要求 18:00"被建议改为 19:00 并待确认，说明普通的指定时间允许提出替代方案；乙在此之上增加 `fixed` 一级：硬性要求被占时连替代草稿都不保存，只请求确认。不填 `fixed` 时行为与参考实例完全一致，不影响任何验收点；真正的时间约束（如"最晚 21:00"）由 `window` 表达 |
| Agent 框架 | LangGraph、AgentScope 等 / 原生实现 | **原生实现** | 循环本身只有几十行；守卫、步数上限、报告汇总都要自己控制，框架带来的抽象在这里没有收益，也不加分 |

## 7. 报告字段的来源

| 字段 | 来源 |
|---|---|
| 审核状态、风险原因、待确认项、任务状态、步数 | **程序**从本次运行的工具调用记录汇总 |
| 草稿状态、时段、版本、是否占位、建议时段 | **程序**读数据库最终状态；本次运行的操作结果另列 `draft.this_run` |
| 时段选择理由、给用户的说明 | 模型 |
| 发布状态 | 恒为 `not_published` |

程序还会校验模型写的文字：如果出现"已发布"，或者某一分句点名了保存失败的素材却声称成功，一律以记录为准，并在 `consistency_warnings` 中标出。

## 8. 步数上限

模型调用轮数与工具调用次数都设有上限（可以配置）。达到上限时，任务状态为 `incomplete`，同时附上已完成的部分和尚未处理的素材。

## 9. 模型接入

- 使用 OpenAI 兼容接口，默认接 DeepSeek（`deepseek-flash`）。通过环境变量也可以切换到通义等兼容服务。
- 模型调用设置超时，`max_retries=0`。失败时直接返回 `error`，不在后台悄悄重试，以免掩盖真实的失败率和延迟。
- 离线 Mock 策略只用来验证流程能走通，不能证明真实模型的决策效果。

## 10. 实现细节清单

设计之外、实现时确定的处理，集中列出便于核对。

**模型交互**

- 参数不是 JSON 对象、缺参数、多参数、类型或枚举不符 → `INVALID_ARGS` 作为观察返回，不执行工具。
- 工具内部异常 → `TOOL_ERROR` 观察，不让整次运行崩溃。
- 模型某轮没有调用工具 → 提醒一次并计入步数（防止只说话不推进而耗尽步数却不报未完成）。
- 上限：决策 15 轮、工具调用 30 次，每轮开始前检查，用尽时不再发起模型请求。
- 模型调用：`temperature=0`、超时 60 秒、`max_retries=0`；客户端初始化失败给出明确错误。
- trace 的返回摘要保留结构，只截断超过 120 字的字符串与超过 16 项的列表；完整结果保留在内部记录中，报告据此汇总。

**时间与时段**

- 可发布时间 09:00–22:00，整点；时段与日期只接受补零写法（`strptime` 也接受 `2026-11-3 9:00`，会绕过主键，见审查 2 #2）。
- 最近空位按与要求时间的距离排序，距离相同取时间较早者；只列守卫会放行的候选。
- 授权 `valid_until` 早于发布日期视为过期，不算补查成功。

**存储**

- 草稿编号 `D-<素材ID>`，每个素材一份草稿；账号变化时同一草稿随之更新。
- "未变化"条件：时段相同、状态相同、且占位仍在（草稿被挤占后同时段重存会重新写入）。
- 正式排期每次启动同步进占位表并优先于草稿；被挤占的草稿标记 `displaced`，报告提示。
- 阻断时在同一事务中撤销草稿并释放占位；草稿已被挤占时不声称释放了时段。
- 锁等待 5 秒，超时返回 `failed`；回滚前检查事务是否仍在，避免掩盖原始错误。
- 故障注入点在"写入已执行、提交之前"，以验证整个事务回滚。

**输入与报告**

- 请求校验：素材不得重复；时间须为补零标准写法；`fixed` 为布尔；`window` 为两个时间且开始不晚于结束。
- `draft` 字段结构固定，无草稿时各值为空。
- 退出码：0 完成 / 2 等待确认 / 1 保存失败、未完成或错误。
- 依赖 `socksio`：系统配置 SOCKS 代理时 openai 客户端需要。

## 11. 开发流程

- **行走骨架（walking skeleton）**：先用固定返回的工具把"循环 → 工具 → 报告 → CLI → CI"端到端跑通，确认结构后再加厚。
- **纵向切片（vertical slice）**：每个切片穿透工具、存储、报告、测试，完成一个验收点：正常排期 → 保存守卫 → 重复提交与并发 → 保存失败 → 补查与规则风险。
- **PR + CI**：每个切片一个 PR，GitHub Actions 强制 `ruff check`、`ruff format --check`、`pytest`。
- **交付前阅卷评审**：冷启动 agent 以阅卷人立场从公开仓库克隆、自建隐藏测试并评分，发现的跨运行问题已修复（[reviews/03-grader.md](reviews/03-grader.md)）。
- **里程碑审查**：骨架完成后、保存层完成后各做一次多 agent 冷启动代码审查（并行找缺陷 → 逐条验证 → 按严重度排序），参照 Claude Code 官方 Code Review 的做法。参数校验与边界类问题直接修复并补回归测试；涉及确认边界、数据来源等语义的问题由我决定修法。记录见 [docs/reviews/](reviews/)。
- **测试分层**：守卫、幂等、并发、失败回滚、报告来源用脚本化假模型做确定性测试（77 项）；"模型会根据工具结果调整"由真实模型运行记录证明。
