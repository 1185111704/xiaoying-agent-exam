# 01 需求分析

## 1. 用户与目标

- **用户**：内容团队的运营人员。手上有一批待处理素材，需要在发布前完成审核，并排进各渠道账号的发布时间表。
- **目标**：对每项素材给出审核结论，形成**无冲突、可确认**的排期草稿。凡是需要人拍板的事项，明确列出来交给人决定。
- **系统边界**：只保存排期草稿，**不发布**。系统里不存在发布工具，任何输出都不得称"已发布"。

## 2. 输入与输出

**输入**（一次排期请求）：

| 字段 | 说明 |
|---|---|
| `request_id` | 请求标识 |
| `items[].material_id` | 素材 ID |
| `items[].publish_at` | 用户指定的发布时间，如 `2026-11-03 18:00` |
| `items[].fixed` | 是否为硬性要求（"必须这个时间"）。默认 `false` |
| `items[].window` | 可选，可接受的时间窗口，如 `["2026-11-03 17:00", "2026-11-03 21:00"]` |

配套材料（合成数据，见 `data/`）：素材库元数据、版权库记录、已有正式排期、审核规则。

**输出**（每项素材一条，另有任务级状态）：

| 字段 | 说明 |
|---|---|
| 审核状态 | 通过 / 阻断 / 信息缺失 / 待人工确认 |
| 风险原因 | 命中的规则编号及原文证据 |
| 建议时段 | 来自实际保存的草稿；未保存时说明原因 |
| 待确认项 | 需要用户拍板的问题及选项 |
| 草稿保存状态 | 已保存 / 未变化 / 已更新 / 冲突 / 被拒 / 失败，以存储层实际返回为准 |
| 发布状态 | 恒为"未发布" |
| 任务状态 | completed / needs_confirmation / save_failed / incomplete / error |

## 3. 需求假设

题目没有给出的信息，按以下假设处理。每条都给出依据，并且可以通过配置调整。

| # | 假设 | 依据 |
|---|---|---|
| A1 | **一个时段为 1 小时，同一账号每个时段只排一条** | 题目没有给时段长度。参考实例是"18:00 被占，建议 19:00"，说明出题方默认的是整点、一小时一个时段。之所以一条内容占满一小时，是因为同一账号的发布之间要留间隔：间隔太近会互相抢流量，也容易触发平台的频率检测；如果是人工发布，还要算上操作耗时。这些都折算进"一小时一条"。时段长度和容量都可以配置 |
| A2 | **冲突来自账号级的业务约束，与发布方式无关** | 题目没有说明是机器发布还是人工发布。机器发布本身是秒级完成的，不存在"发不完"的问题；但同一账号仍然不能连续发布，所以冲突照样存在。不少平台会检测脚本发布，很多团队仍然手动发，但无论哪种方式，约束条件都一样 |
| A3 | **"指定时间"默认可以替换，"硬性要求"不能擅自改** | 参考实例里"要求 18:00"被替换成 19:00 并标记待确认，说明指定时间默认允许给出替代方案，但必须交给用户确认，且原始要求要保留。只有明确标注 `fixed` 的才是硬性要求，改动前必须拿到用户确认。替代时段默认**只能顺延**：提前发布可能违反活动或保密时间；用户可通过 `window` 显式允许提前 |
| A4 | **需求量小，单机即可** | 一个内容团队的素材量在几十条/天这个量级。用单机 SQLite 保证并发安全，不做缓存、分级或分布式锁 |
| A5 | **审核规则为合成数据** | 题目没有给具体规则，项目自建一份示意规则，不代表真实的审核标准 |

## 4. 审核范围

### 4.1 字段校验：分三档

由程序判定字段属于哪一档，这是事实层面的判断。拿到事实后下一步怎么做，由模型决定。

| 档位 | 字段 | 处理 |
|---|---|---|
| 直接打回 | 素材不存在、渠道/账号缺失、文案缺失 | 无法排期，不能保存 |
| 可以补查 | 音乐授权、肖像授权 | 素材库里为空，但版权库可能有记录。由模型决定是否补查；补查不到时，由模型选择请求确认或阻断 |
| 待补充 | 封面、标签 | 不影响排期，列入待确认项 |

### 4.2 内容规则

真实业务中的内容审核通常分多层：关键词过滤、分类模型、人工复审。本项目只实现**确定性的词表检查**，例如广告法极限词，返回命中的规则和原文证据，结果可以稳定复现。语义层的审核（如没有依据的效果宣称）属于后续扩展：业务信息不足，规则只能靠编，评审也无从判断好坏。

## 5. 不在范围内

真实发布；界面；LLM 语义审核；同一批多个素材抢同一时段时的优先级策略；占位超时自动过期；分布式部署。

## 6. 成功标准

### 6.1 必须验收

| 验收点 | 判定标准 | 用例 |
|---|---|---|
| 正常排期 | 无风险素材排进指定时段，草稿已保存，无待确认项 | `examples/01-normal` |
| 素材信息缺失 | 缺必需字段的打回；缺授权的先补查，补到则继续，补不到则请求确认 | `examples/02-missing-info` |
| 规则风险 | 命中词表的素材被阻断，报告附规则编号和原文证据 | `examples/03-rule-risk` |
| 时段冲突 | 指定时段被同账号占用时，给出替代时段并标记待确认；硬性要求不擅自改动 | `examples/04-conflict` |
| 重复提交 | 同一请求再次运行只有一份草稿；已在正式排期中的素材再次提交被识别出来 | `examples/05-duplicate` |
| 保存失败 | 明确返回失败，不称成功，已占的时段回滚 | `examples/06-save-failure` |

逐项的实际结果见 [03-evaluation](03-evaluation.md)。

### 6.2 隐藏测试："更换占用时段并重复提交"

修改排期数据后原样再提交，结果应随之变化，且草稿始终只有一份：

- 替代时段也被占了：同一份草稿换到下一个空位，版本号加 1。
- 原指定时段被释放了：草稿回到原时段，取消待确认。

对应 `examples/07-resubmit`（同一请求在同一状态库上运行三次，每次之前修改正式排期）。

### 6.3 关键缺陷（一律不允许）

- 越权发布：系统里没有发布工具，输出中不得出现"已发布"。
- 虚报保存成功：保存状态只取存储层的实际返回，模型自己的说法不作数。

### 6.4 其他硬性要求

- 有执行步数上限，达到上限时返回 `incomplete`（`examples/08-step-limit`）。
- 至少两条执行路径的真实模型运行记录，能看出模型根据不同的工具结果调整了下一步动作。
