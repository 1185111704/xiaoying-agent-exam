# 05 复盘

## 1. 最难的问题：既要模型真正决策，又不能把底线押在模型上

题目有两条互相牵制的要求：一是"仅有固定条件分支不算 ReAct"，下一步必须由模型决定；二是"越权发布、虚报保存成功"属于关键缺陷，不能靠模型自觉避免。

设计初稿把大量判断放进程序守卫。冷启动评审指出了风险：程序替模型做的分支越多，trace 越像"固定分支 + LLM 装饰"。最终确定的原则是 **程序只否决，不替模型选路线**：

- 程序给事实（缺什么、命中什么、谁占了时段、保存是否成功），并拒绝非法动作；
- 拒绝原因作为观察交还模型，由模型决定补查、换时段、请求确认、阻断或如实上报；
- 报告只采信工具记录与数据库，模型的文字只作说明并被校验。

这个原则在真实运行中得到验证：模型两次选了提前的时段，被守卫拒绝后自行顺延；漏处理素材就想结束，被拦下后补上了阻断。底线由程序守住，而"被拒之后怎么调整"成了 trace 中可见的决策。

## 2. 第二难：幂等键的语义

"相同请求重复保存只产生一份草稿"看似简单，但设计初稿只写了这句要求，没有定义幂等键基于什么。评审推演出反例：如果键里包含模型选出的时段（例如按草稿内容判重），第二次提交时 19:00 已被自己的旧草稿占住，模型会改选 20:00，于是生成第二份草稿，正好违反要求。改用业务键（素材, 账号）后，内容变化体现为同一草稿升版本；再配合"查询时排除自己的占位"，重复提交和"更换占用时段再提交"都只保留一份草稿。

这个问题在写代码之前就被发现，是设计阶段做多视角评审最直接的收益。

## 3. 收获

- **测试证明保证，trace 暴露缺失的规则。** 75 项确定性测试能证明"冲突不会发生、失败不会报成功"，但"替代时段该往前还是往后"这种没被建模的业务约束，只有读真实运行的 trace 才看得出来。两者缺一不可。
- **行走骨架让结构问题暴露得最早。** 骨架阶段就确定了报告格式、trace 字段和"错误作为观察返回"的约定，之后每个切片只往里加内容，没有返工结构。
- **审查要分级处理。** 两次多 agent 审查共 20 项发现，其中真正改变设计的只有几项（报告采信模型标记、报告读数据库）。边界类问题直接修，语义类问题由人决定，审查的时间成本可控。
- **客观约束都应进程序。** 是否需要确认、时段能否提前、占用情况，这些都能客观判定；凡是交给模型"自觉"的，最终都在审查或 trace 中出了问题。

## 4. 未完成与下一步

按优先级：

1. **第二轮确认**：`--confirm C1=accept|<时段>` 把待确认草稿推进为 `confirmed`（同一草稿升版本），硬性要求凭确认凭证才可改。设计已完成（02 §5），未实现。
2. **确认项的占用情况按最终状态重算**：目前是登记时的快照，同一次运行中后续保存可能使选项失效（见 03 §5）。
3. **稳定性评估**：每个用例多次运行真实模型，统计各验收点的通过率，而不只看单次 trace。
4. **审核能力**：在词表之外加入 LLM 语义审核（无依据的效果宣称等），输出结构化证据，并离线 Mock 保证测试稳定。
5. **排期策略**：同批多个素材抢同一时段时的优先级；草稿占位超时释放；多机部署时迁移到 PostgreSQL（表结构与唯一约束可直接沿用）。
